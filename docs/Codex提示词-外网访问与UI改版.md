## 附：给你（用户）的说明

### 为什么这么写

| 写法 | 用意 |
| --- | --- |
| 第 0 步强制读三份文档 | Codex 新会话没记忆，不读就会乱猜架构 |
| 把"能用但很慢"写进现状 | 这是关键症状——不是连不上，排障方向完全不同 |
| 列出 6 个我已定位的可疑点 + 行号 | 省掉 Codex 一半的探索，直接进验证阶段 |
| 要求"区分本机慢 vs 外网慢" | 不区分就会误把花生壳带宽问题当代码问题改 |
| 要求"如实说带宽是不是硬瓶颈" | 防止 Codex 用改代码来掩盖一个网络层问题 |
| "不要引入付费方案替代" | 你只是演示，不该为提速花钱 |
| UI 明确"不推翻风格" | 你选了保留暗色精修，不写死这条 Codex 很可能自己换风格 |
| UI 要求六维体检 + 带行号 | 避免"可以更美观"这类无信息量的输出 |
| "只出方案不改代码" | 你惯用的「只读审计 → 确认 → 再执行」节奏 |

### 需要你补一句的地方

提示词里我按已知信息写死了 6 个可疑点。如果你之后自己发现了别的现象
（比如"只有第一次打开慢，刷新就快"→ 那是缓存问题；或"所有页面都慢"→ 是带宽），
把现象贴进提示词开头，Codex 的定位会更准。
